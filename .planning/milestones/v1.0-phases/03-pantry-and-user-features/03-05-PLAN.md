**Match Pantry API** (`server/api/recipes/match-pantry.get.ts`):
- Accept query params: `ingredients` (comma-separated ingredient names) and optional `restrictions` (comma-separated dietary restriction tags)
- This endpoint does NOT require auth -- it works with ingredient names passed as params (supports both guest and auth users)
- If no ingredients provided, return empty array
- Fetch all recipes from D1 (< 10k rows, in-memory filtering per research recommendation)
- For each recipe:
  1. Parse recipe.ingredients JSON array
  2. For each recipe ingredient, check if any pantry ingredient name is contained in it (case-insensitive substring match)
  3. Calculate matchPercent = matchedIngredients / totalIngredients * 100
  4. If `restrictions` provided, parse recipe.dietaryTags and check that all user restrictions are present. Skip recipes that don't meet restrictions.
- Filter: only return recipes with >= 50% match
- Sort by matchPercent desc, then by recipe title asc
- Return top 20: `Array<{ recipe: Recipe, matchPercent: number, matchedCount: number, totalCount: number }>`
- Cache in KV with key `match:{hash(ingredients+restrictions)}` and 5-minute TTL
- Parse JSON fields on recipe objects before returning

**PantryMatches component** (`app/components/PantryMatches.vue`):
- Props: `ingredients: Array<{name: string}>`, `restrictions: string[]`
- Watch ingredients and restrictions -- when either changes, fetch from `/api/recipes/match-pantry?ingredients=...&restrictions=...`
- Debounce the fetch by 500ms (user might be adding multiple ingredients rapidly)
- Display results as a list of RecipeCard components, each with a match percentage badge
- Match badge: rounded pill showing "85% match" in green (>= 80%), yellow (>= 60%), orange (>= 50%)
- Empty state when pantry has items but no matches: "No matching recipes found. Try adding more ingredients!"
- Empty state when pantry is empty: don't show this section at all
- Loading skeleton while fetching

**Pantry page update** (`app/pages/pantry.vue`):

- Section heading: "Recipes You Can Make"
- Pass current pantry ingredients and dietary restrictions from usePantry composable

The guest-to-auth migration is tricky because `onLinkAccount` runs server-side but guest data lives in client localStorage. The research recommends a two-step approach:

**Step 1: Client-side migration endpoint** (`server/api/user/migrate-guest-data.post.ts`):
- Require authenticated non-anonymous user
- Accept body: `{ pantryItems: Array<{ingredientId: string, ingredientName: string}>, dietaryRestrictions: string[] }`
- Insert pantry items into pantryItems table (skip duplicates by checking ingredientId per user)
- Replace dietary restrictions (delete existing, insert new)
- Return `{ migratedPantryCount: number, migratedRestrictionCount: number }`
- This endpoint is called by the client after successful signup/login linking

**Step 2: Update auth.ts onLinkAccount** (`server/lib/auth.ts`):
- Keep the existing onLinkAccount callback but add a log message noting that client-side migration handles the data transfer
- The actual data migration happens client-side: after a guest user links their account (signs up), the client detects the transition from anonymous to authenticated and calls the migrate endpoint with localStorage data, then clears localStorage

**Step 3: Client-side migration trigger** -- add to `app/composables/usePantry.ts` (already created in Plan 02):
- In usePantry, watch for session changes (anonymous -> authenticated)
- When detected: read guest_pantry and guest_dietary_restrictions from localStorage
- If data exists: POST to `/api/user/migrate-guest-data`
- On success: clear localStorage keys (guest_pantry, guest_dietary_restrictions)
- This is a one-time migration that fires automatically

Note: Since usePantry.ts is already created in Plan 02, this task should READ the existing file and ADD the migration logic. Add a `watchEffect` or `watch` on the session that triggers migration when `session.user` changes from anonymous to non-anonymous.
