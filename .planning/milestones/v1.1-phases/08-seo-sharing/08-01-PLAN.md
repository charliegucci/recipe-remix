  <action>
1. Install slugify: `npm install slugify`

2. Create `server/utils/slug-generator.ts`:
   - Export `generateSlug(title: string): string` that uses `slugify(title, { lower: true, strict: true })` to produce a base slug
   - Export `generateUniqueSlug(title: string, existingSlugs: Set<string>): string` that appends `-2`, `-3` etc. for duplicates
   - Keep slugs 2-6 words (truncate after 60 chars if needed, break at word boundary)

3. Update `server/db/schema.ts` — add `slug` column to the `recipes` table:
   ```typescript
   slug: text('slug').notNull().unique()
   ```
   Also add a slug index in the table's index function.

4. Run `npx drizzle-kit generate` to create the migration SQL. The migration will be in `server/database/migrations/`. Since existing rows have no slug, the migration needs manual editing:
   - The generated SQL will fail because existing rows have no slug value. Edit the migration to:
     a. `ALTER TABLE recipes ADD COLUMN slug TEXT;` (nullable first, no constraint)
     b. Do NOT add the unique constraint or NOT NULL yet — that happens after slug generation.
   - Create a second migration file `0007_add_slug_unique_index.sql` with:
     ```sql
     CREATE UNIQUE INDEX recipes_slug_idx ON recipes(slug);
     ```
     This will be applied AFTER slugs are generated.

5. Create `server/api/_seeds/generate-slugs.post.ts` — a one-time endpoint to generate slugs for all existing recipes:
   - Query all recipes (id, title) from D1
   - Use `generateUniqueSlug` to create slugs, tracking used slugs in a Set
   - Update each recipe's slug column individually (D1 batch may fail — use individual updates per project pattern)
   - Return count of updated recipes
   - This endpoint should be called once during migration, then can be removed

6. Apply the first migration locally: `npx nuxi dev` will auto-apply pending migrations via NuxtHub's D1 stubbing. Alternatively, run `npx drizzle-kit push` if migrations are applied that way.

7. Call the seed endpoint to populate slugs: `curl -X POST http://localhost:3000/api/_seeds/generate-slugs`

8. After slugs are populated, apply the unique index migration.

IMPORTANT: The project uses NuxtHub's automatic D1 management, so migrations may auto-apply on dev start. Check how previous migrations were applied (files 0000-0005 exist in server/database/migrations/).
  </action>

   - Get param as `idOrSlug` via `getRouterParam(event, 'idOrSlug')`
   - First, try lookup by slug: `db.select().from(schema.recipes).where(eq(schema.recipes.slug, idOrSlug)).get()`
   - If not found AND `idOrSlug` matches `/^\d+$/` or looks like a UUID (the project uses text IDs), try by ID: `where(eq(schema.recipes.id, idOrSlug))`
   - If found by ID, return 301 redirect: `return sendRedirect(event, \`/api/recipes/${recipe.slug}\`, 301)` — actually NO, the API should return data, not redirect. The API should just return the recipe data regardless of lookup method. The PAGE redirect is handled by middleware.
   - Actually, keep it simple: try slug first, then ID fallback. Return recipe data either way. The API is consumed by the page, and the page URL is what matters for SEO.
   - Update KV cache key to use slug: `recipe:${recipe.slug}` (or keep using ID for cache, either works)
   - Keep all existing logic (JSON parsing, aggregate ratings, KV caching)

2. Create `server/middleware/legacy-redirects.ts`:
   - Match URL pattern `/recipe/` followed by what looks like a non-slug identifier
   - Since recipe IDs are UUIDs (text), detect them: if the path segment matches UUID pattern or is purely numeric, look up the recipe by ID in D1
   - If found, `sendRedirect(event, \`/recipe/${recipe.slug}\`, 301)`
   - If not found, let request continue (will 404 naturally)
   - IMPORTANT: Only intercept page routes (`/recipe/...`), NOT API routes (`/api/recipes/...`)

3. Rename `app/pages/recipe/[id].vue` to `app/pages/recipe/[slug].vue`:

   - The recipe API still needs the ID for some sub-endpoints (image, substitute, reviews). After fetching the recipe by slug, use `recipe.value.id` for those endpoints.
   - Update the `useHistory().recordView()` call to use `recipe.value.id` (history tracks by ID internally)
   - Keep ALL existing template markup, styling, and logic unchanged

4. Update all internal links to use slugs instead of IDs. The recipe list API (`/api/recipes/index.get.ts`) needs to return the `slug` field. Then update:
